# 区块提测自动化模型

## 核心认识

区块不能只按 `BLOCK_ID` 做一套完全相同的检查。每个区块同时具有：

1. **所有区块共有的通用属性**：添加、保存、预览、渲染、基础样式与链接/图片等规则。
2. **所属类别的共性**：例如图文、产品/文章、表单、图片集、页头、视频 Banner 等类别各自的检查项。
3. **数据模式的共性**：静态区块主要验证编辑内容；动态区块从内容管理取数，还要验证数据来源、筛选/排序、状态变化和无数据场景；混合区块两者都有。
4. **单个区块的专属功能**：以该区块的 Figma 设计稿、原型说明和业务规则为准，验证独有的元素、状态、交互和展示逻辑。

因此，提测自动化采用“通用套件 + 类别/数据套件 + 区块专属套件”的组合，而不是给每个区块从零写一份脚本，也不是只跑一套无差别检查。

## 核心复用单位：设置项能力模块

复用的最小单位不是区块，而是**设置项能力**。每个设置项（如「选择自定义筛选字段」「显示条数」「排序方式」「是否显示图片」）沉淀为一个标准能力模块，包含一份可执行契约：

- **识别**：在编辑器里如何定位这个设置项、它有哪些选项/取值范围
- **参数**：要测的取值（默认值、每个关键选项、边界与组合），以及变体（如单选/多选）
- **动作**：如何设置、保存、预览
- **断言契约**：设置值 → 前台可观察效果（DOM、样式、数据集合的变化）
- **前置条件**：需要的测试数据、依赖的其他设置项
- **证据**：报告中的归类、截图点位

新区块提测时，画像只需声明它拥有哪些能力及各自参数，运行器就自动组合出对应的验证脚本；同一个设置项在第二个区块出现时零新增代码。只有真正独有、且不对应任何设置项的逻辑才写专属检查；当某个专属检查在第二个区块被复用时，就把它提升为新的能力模块（“第二次复用即沉淀”）。

能力模块的验证分三层，缺一不可：

1. **设置层**：设置项存在、选项与默认值与 Figma/规格一致、能修改、保存后重开仍保持；
2. **效果层**：保存预览后，该设置值在前台产生的效果与契约一致；
3. **数据层**（动态区块）：前台结果与内容管理数据按规则独立计算出的预期集合（oracle）一致，而不是只看“页面变了”。

设置项之间会互相影响，组合策略按风险收敛：每个能力先单独测（默认 + 关键非默认取值），只有存在依赖关系的能力才做两两组合，不做全量笛卡尔积。每个场景结束后恢复默认配置，保证用例互相独立、可重复跑。

## 区块画像（Block Profile）

每个提测区块先建立一份画像，作为测试选择和专属断言的唯一入口。建议字段：

- `blockId`、名称、版本/提测批次
- `category`：业务类别，如产品、文章、图文、表单、图片集、页头、视频 Banner
- `dataMode`：`static`、`dynamic` 或 `hybrid`
- `dataSource`：内容管理中的实体与范围，如产品、文章、分类、表单数据
- `targetPage`、站点、语言
- `interactions`：筛选、搜索、轮播、分页、标签切换、表单提交等
- `figma`：设计稿链接、节点、版本
- `testData`：需要预置的数据及关键状态
- `specificChecks`：从 Figma/业务规则提炼的专属检查，必须标明断言来源和是否已确认

画像可以先由 Muse 根据区块信息和 Figma 初稿生成，但涉及业务含义的断言需要人工确认后再进入稳定套件。

## 套件分层

### A. 通用套件（所有区块）

- 区块可添加、保存、预览并在目标页面正确出现
- 基础 DOM/CSS 规则：字体、折行、图片 alt、链接 href、可点击手型等
- `css-font-follow` 与 `css-word-break` 两项 CSS 检查按用户 2026-10-23 决策只取证记录、不判 fail：读取到 CSS 时记为 `record`，无法取证时记为 `skip`，不参与失败判定。
- 宽度/布局、复制、删除等生命周期能力（按阶段逐步接入）
- 多语言/RTL、响应式等平台级规则（按阶段逐步接入）
- 只截图留证、不做硬断言的视觉项：美观、清晰度、播放流畅度等

### B. 类别套件（同类区块共享）

按 `3.0.xlsx` 中已有的分类方式复用：通用 + 图文 / 产品·文章 / 表单 / 图片集 / 页头 / 视频 Banner 等。类别套件只写一次，新区块按类别自动带入。

### C. 动态数据套件（动态/混合区块）

动态区块的重点不是“页面上有这个容器”，而是“页面拿到的数和发生的业务变化是否正确”：

- **数据来源**：展示内容与内容管理中指定的数据范围一致，未发布/不属于该范围的数据不出现
- **字段映射**：标题、图片、摘要、价格、分类、时间等字段与内容管理记录对应
- **数量与排序**：展示条数、排序规则、置顶/推荐等规则正确
- **筛选与搜索**：单条件、多条件组合后的结果与预期数据集一致
- **分页/加载更多**：页数、条数、边界页和重复/遗漏
- **状态变化**：选择、重置、清除、展开/收起等操作后结果正确恢复或更新
- **边界数据**：0 条、1 条、大量数据、无图、长标题、特殊字符、缺失字段
- **空状态**：没有符合条件的数据时显示设计稿规定的空状态，不报错、不残留旧结果

动态套件运行前必须有可识别的测试数据。优先使用内容管理中预置的固定数据集，并给每条数据设置可追踪的标题/编号；不能拿线上随机数据做精确断言。

### D. 区块专属套件（单个区块）

从 Figma 和业务规则中提炼，常见来源包括：

- 设计稿中的组件、文案、图标、按钮和字段是否齐全
- 默认、选中、悬停、展开、收起、禁用、空数据等状态
- 设计变量：颜色、字体、字号、间距、圆角、尺寸和断点
- 原型交互：点击后发生什么、跳转到哪里、哪些区域联动
- 该区块独有业务规则：显示条件、数量限制、计算方式、筛选逻辑、排序和异常处理

Figma 能证明“设计长什么样、有哪些状态”，但不总能证明业务逻辑。仅凭静态设计稿无法确定的行为，应标记为待确认，不直接写成硬断言。

## 提测时的输入包

一个区块提测时，尽量一次提供：

1. 区块 ID、名称和所属类别
2. Figma 链接，最好精确到对应区块/画板节点
3. 目标站点、页面和语言
4. 数据模式；若为动态区块，说明内容管理的数据来源和范围
5. 已准备的测试数据，或需要 Muse 协助设计的数据清单
6. 区块配置项及默认值（例如显示条数、是否显示某个字段）
7. 原型交互说明、需求说明或开发自测说明（有则提供）

## 执行流程

1. **建立画像**：读取区块参数、Figma 节点和已有说明，生成 Block Profile 草案。
2. **生成检查清单**：自动组合通用套件、类别套件、动态数据套件，并列出专属检查候选。
3. **确认关键断言**：业务逻辑、预期数据和 Figma 中不明确的状态先确认，避免把猜测写成断言。
4. **准备数据**：动态区块按数据集清单检查内容管理中的记录是否齐全、是否可识别。
5. **执行测试**：添加/配置区块，保存、预览，按分层套件执行并保留截图与结构化报告。
6. **输出报告**：结果按通用 / 类别 / 动态 / 专属分组；失败项附实际数据、期望来源和截图，方便开发定位。

## 40838 的定位

40838 是产品筛选类动态区块，数据来自内容管理。它除通用检查外，还应重点验证：可选分类/筛选项与内容管理数据一致、筛选组合能正确缩小结果、Reset/Clear 能恢复、所选展示数据范围正确，以及无匹配数据时的状态。具体筛选项、结果联动方式和空状态文案仍需以它的 Figma/业务说明为准确认。
